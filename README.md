# АРМ КМК: журнал заказов и отметка выработки

Расширение для проекта EDT `УНФ_Демо_КМК`, платформа 8.5.1. Исходники находятся в `АРМ_для_КМК`. Это расширение, а не самостоятельная конфигурация: для сборки и запуска нужен базовый проект УНФ.

## Что изменено

- Журнал показывает одну сводную строку заказа: номер, участок, первое изделие с `+N`, общий план, выполнено, остаток и рассчитанный статус.
- Оператор видит участки своего допуска, мастер — все, контролёр — предопределённый участок «Контроль». При нескольких ролях приоритет: мастер, контролёр, оператор. В журнале показаны роль и работник.
- Пользователь с платформенным правом **«Администрирование»** может открывать журнал и видеть все участки без ролей расширения и без записи в регистре работников. Этот доступ имеет приоритет над производственными ролями. В шапке при отсутствии сотрудника показано имя входа пользователя ИБ. Имя учётной записи «Администратор» само по себе прав не даёт.
- Поиск по части номера и отбор статуса работают совместно; счётчик показывает результат отбора. Для применения введённого номера завершите ввод поля (Enter/переход в другое поле).
- Кнопка «Взять в работу» и выбор строки двойным щелчком/Enter открывают форму выработки. Само открытие не меняет заказ или статус.
- В форме семь колонок. Редактируются только целые неотрицательные количества «Выполнено сейчас» и «Брак». Шапка и расчётные поля защищены; добавление и удаление строк отключено.
- После изменения количества остаток пересчитывается; отрицательный подсвечивается красным. Превышение запрещается и клиентом, и сервером.
- «Записать» проводит **отдельный новый документ для каждой порции**, увеличивает ранее выполненное, обнуляет ввод и оповещает открытый журнал. «Записать и закрыть» дополнительно закрывает форму. Закрытие/крестик не записывают ввод.
- При записи сервер проверяет текущего работника, доступ к участку, строку заказа, целочисленность и актуальный остаток под блокировкой. Данные формы не считаются достоверным источником плана и ранее выполненного.
- Движения разделены по заказу, участку и номеру строки продукции; одинаковые изделия разных строк больше не объединяются в одну выработку.

Статус рабочего места рассчитывается из выработки. Типовое `СостояниеЗаказа` УНФ не изменяется: иначе открытие заказа или операция участка могли бы менять независимый процесс основной конфигурации.

## Подготовка тестовой базы

1. Сделайте резервную копию базы. Подключите в EDT базовый проект `УНФ_Демо_КМК`, затем импортируйте проект расширения из каталога `АРМ_для_КМК`.
2. Выполните проверку проекта EDT вместе с основной конфигурацией. В базовом `ЗаказНаПроизводство` должны существовать табличная часть `Продукция` и её поля `Номенклатура`, `Характеристика`, `Количество`. Используется также добавленный расширением реквизит заказа `Участок`.
3. Перед применением изменения типов количеств проверьте старые документы `Выработка`: поля «Выполнено» и «Брак» переводятся с точности 3 на 0. **Если в базе есть дробная историческая выработка, не применяйте сужение типа без отдельного согласованного переноса данных.** Автоматический перенос и округление здесь не выполнялись.
4. Обновите расширение в тестовой базе. Назначьте пользователям подходящие роли расширения. Роли основной конфигурации для запуска УНФ также необходимы; роли расширения не заменяют их.
5. Под пользователем с ролью «Мастер» откройте раздел **«Производство КМК» → «Работники пользователей КМК»**. В новом регистре `Расш1_РаботникиПользователей` задайте для каждого пользователя:
   - `ИмяПользователяИБ` — **имя входа пользователя информационной базы**, не полное имя и не email, если они отличаются;
   - `Работник` — соответствующий элемент справочника «Сотрудники».
6. В регистре «Допуски сотрудников» задайте разрешённые участки операторов. Контролёр использует предопределённый участок `Контроль`, мастер — все непомеченные на удаление участки. У заказов должен быть заполнен `Участок`.
7. Откройте **«Производство КМК» → «Журнал заказов в работу»** и выполните сценарии из [docs/acceptance.md](docs/acceptance.md).

Для обычных пользователей отсутствие сопоставления сотруднику приводит к понятной ошибке. Администратор может просматривать журнал и ранее записанную выработку без сопоставления; для создания и записи новой порции сотрудник обязателен. Проверка исполнителя остаётся в серверном модуле объекта и не обходится администраторским просмотром. После переименования учётной записи обновите сопоставление.

## Раздел интерфейса

Добавлена явная общая команда открытия журнала в существующую подсистему расширения `АРМ_КМК`, отображаемую как **«Производство КМК»**. Включение одной общей формы в состав подсистемы не создаёт надёжную команду открытия само по себе.

Для размещения команды именно внутри **типового** раздела УНФ «Производство» нужно в EDT заимствовать соответствующую подсистему из вашей основной конфигурации и включить команду `Расш1_ЖурналЗаказовВРаботу` в её состав/командный интерфейс. UUID заимствуемых объектов из неизвестной версии УНФ в коде не выдумывались. Команда уже доступна через собственный раздел, так что это не блокирует проверку функций рабочего места.

## Историческая выработка

В регистр и табличную часть документа добавлено поле `Расш1_НомерСтрокиЗаказа`. Новые записи заполняют его автоматически.

У старых движений поле будет равно нулю. Такие движения учитываются по старой паре «номенклатура + характеристика» **только если она однозначно определяет одну строку заказа на данном участке**. Старые документы при этом не изменяются и не перепроводятся.

Если одинаковое изделие было в нескольких строках или строки/участок заказа изменены, программа останавливает расчёт с указанием проблемного заказа. Нужно отдельно установить принадлежность старых движений строкам на копии базы и выполнить проверенный перенос. Молчаливое распределение, игнорирование старых количеств и массовое перепроведение не используются.

Номер строки — идентификатор строки текущего заказа. После начала учёта не переставляйте и не заменяйте продукцию в заказе без отдельной процедуры корректировки выработки. Маршрут одного заказа сразу по нескольким участкам требует отдельной модели: текущая основа хранит один участок в шапке заказа.

## Принятые правила и границы

- Как в текущем ТЗ и HTML: брак уменьшает остаток при вводе текущей порции, но не увеличивает «Выполнено» в журнале. Накопленный брак хранится отдельно в регистре; остаток журнала равен плану минус годные единицы. Изменение этой схемы требует согласования перевыпуска.
- При нулевом вводе документ не создаётся, выводится «Нет данных для записи.». Полностью выполненные заказы остаются доступны через статус «Выполнен» и «Все».
- Старые документы, открытые по ссылке, доступны в форме только для просмотра. Новая порция создаётся из журнала; стандартная запись/Ctrl+S не подменяет команды рабочего места.
- Простои, марки и расчёт оплаты не удалены из метаданных/существующей логики, но дополнительные поля убраны с компактной формы по этому ТЗ. Дополнительный функционал не считается проверенным этой доработкой.
- Разграничение списка и запись проверяются на сервере рабочего места. Полноценные RLS-ограничения всех стандартных списков УНФ и регистров не вводились; права других ролей основной конфигурации нужно проверять отдельно.
- Фактический вид вкладок и адаптация на смартфоне проверяются в запущенной 1С. Одних XML/BSL для этого недостаточно.

## Доступные автоматические проверки

Из корня репозитория:

```bash
python3 -m unittest discover -s tests -v
```

Проверяются XML, состав колонок, запреты редактирования, привязки событий и контексты обработчиков, права, ссылки метаданных и типы чисел. Это **структурные проверки**, не исполнение сценариев 1С.

Для синтаксического/статического анализа можно использовать BSL Language Server:

```bash
mkdir -p /tmp/edt-bsl-report
java -jar /path/to/bsl-language-server.jar analyze \
  -s АРМ_для_КМК/src -w АРМ_для_КМК -o /tmp/edt-bsl-report -r json
```

В облачной среде нет платформы 1С, EDT и основной конфигурации. Статический анализ не подтверждает компиляцию расширения, валидность всей модели EDT, доступность полей конкретной версии УНФ, работу транзакций или прохождение приёмки в базе. Перед рабочим применением обязательны проверка EDT и сценарии на тестовой базе.
